# StrawberryShake.Transport.Http repro (16.7.5)

Minimal reproduction for four problems in `StrawberryShake.Transport.Http` / `StrawberryShake.Core` 16.7.5.
No server is needed: a stub `HttpMessageHandler` returns a fixed `application/json` body.

Issues:
- https://github.com/ChilliCream/graphql-platform/issues/10853 (`thread`: parse on the caller's context)
- https://github.com/ChilliCream/graphql-platform/issues/10854 (`alloc`: double parse, document never disposed)
- https://github.com/ChilliCream/graphql-platform/issues/10855 (store-less executor and `@defer`/`@stream` patches; from the source, no mode here)
- https://github.com/ChilliCream/graphql-platform/issues/10856 (`internal-error`)

- `src/Repro`: console app. A client is generated by `StrawberryShake.Server` 16.7.5 from a toy schema (`points { x y }`).
- `fix/StrawberryShake.Transport.Http`: the 16.7.5 transport sources with a proposed change in `ResponseEnumerable.cs` (marked `PROPOSED FIX`). Build with `-p:WithFix=true` to use it instead of the package.

## Run

```bash
cd src/Repro
dotnet run -c Release -- thread           # where the result is parsed and built
dotnet run -c Release -- alloc            # allocation per call, 30,000 points
dotnet run -c Release -- internal-error   # 200 whose only error is "Internal Execution Error"
dotnet run -c Release -- hash             # digest of the parsed result, plus an error/extensions case

dotnet run -c Release -p:WithFix=true -- thread   # same modes, with the proposed transport change
```

## Results (.NET 10.0.9, Apple M5, Release)

| Mode | 16.7.5 package | With the proposed change |
|---|---|---|
| `thread`: thread the result builder runs on, when `ExecuteAsync` is awaited on a single-threaded `SynchronizationContext` and the headers arrive on a pool thread | the context thread | a pool thread (the caller still resumes on the context thread) |
| `alloc`: allocated per `ExecuteAsync`, 1,644,299-byte body, 30,000 points | 17,678 KB, 12.0-12.5 ms | 5,462 KB, 6.4 ms |
| `alloc`: one `JsonDocument.ParseAsync` of the same body, disposed / not disposed | 0 KB / 6,145 KB | same |
| `hash`: SHA-256 of all parsed points; error message, code, path; extensions | `671CEB99…`, `boom code=X path=points`, `k` | identical |
| `internal-error` | `System.ArgumentNullException: Either body or exception have to be set. (Parameter 'data')` | not changed by this patch |

## What the proposed change does

In `ResponseEnumerable.GetAsyncEnumerator`:

1. `ConfigureAwait(false)` on the `client.SendAsync` await.
2. For a successful, UTF-8 `application/json` or `application/graphql-response+json` response: one `JsonDocument.ParseAsync` straight from the content stream, passed to the result builder. This replaces the HotChocolate parse followed by the write-back and second parse in `ParseResult`.
3. Dispose that document in a `try`/`finally` around the `yield`, after the executor has built the result. The JSON scalar (`AnySerializer.Parse`) clones its value, and errors/extensions are copied, so the built result keeps no reference into the document.
4. Every other response (non-2xx, other content types, incremental delivery) keeps the original path, so `@defer`/`@stream` patching is untouched.
